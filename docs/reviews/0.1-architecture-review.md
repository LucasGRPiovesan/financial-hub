# Review 0.1 — Architecture & Financial Model (independent, adversarial)

> Task Q0.1 · Reviewer roles: fintech ledger/payments domain expert + staff engineer · Date: 2026-10-10
> Inputs: PLAN, ARCHITECTURE, DOMAIN, FINANCIAL_MODEL (FM), INTEGRATIONS, SECURITY, ADR-0001..0011, research/*.
> Verdict: **the ledger primitives are sound; the posting recipes are not yet safe to implement.** 4 blockers and
> ~20 majors, concentrated in provider-split refunds, wallet top-ups, and at-most-once provider calls.
> Asaas facts cited as `asaas §n` refer to `docs/research/asaas-sandbox.md`.

## 1. Ledger correctness

### 1.0 Primitives and chart of accounts
- Account types / normal balances: all 11 accounts in FM §3 have the correct type and normal side. OK.
- FM §2 `available = posted minus pending outflows (in its normal direction)` is correct. **PLAN §4 #3 says
  `available = posted − pending_debits`**, which is only right for credit-normal accounts (wrong for any asset
  account that ever gets a hold). Make PLAN point at FM §2.
- Missing accounts that the recipes implicitly need (details below): `customer_unapplied_cash:{c}` (overpayment /
  late payment on a dead intent), `payee_receivable:{p}` (clawback; FM R8 says "recoverable item" but books an
  expense), `late_fee_income` / `discounts_given` (Asaas `value` ≠ billed amount), `refunds_in_flight:{pa}`,
  `provider_suspense:{pa}` (money with no matching intent), `equity:opening_balance` (the sandbox account starts
  with test money — asaas §1 "adicionar dinheiro para testes" — so reconciliation breaks on day one without an
  opening entry).

### 1.1 Recipe-by-recipe

| Recipe | Balances? | Verdict | Findings |
|---|---|---|---|
| R1 | Yes (`T−u` = `T−u`) | **Finding** | F-07, F-12, F-13 |
| R2 | Yes (G=G, F=F) | **Finding** | F-08, F-09 |
| R3 | Yes (G = Σs_i + (G−Σs_i)) | **Finding** | F-02, F-08, F-10, F-11 |
| R4 | Yes (N=N, s_i=s_i) | **Finding** | F-08, F-14 |
| R5 | Yes | **Finding** | F-05, F-10 |
| R6 | Yes (A=A) | **Blocker** | F-02 |
| R7 | Yes (u=u, then R3) | **Finding** | F-06 |
| R8 | Yes ((R−Σs') + Σs' = R) | **Blocker** | F-01, F-15, F-16, F-17 |
| R9 | Yes (each leg) | **Finding** | F-18 |
| R10 | Yes (P=P) | **Finding** | F-03, F-19 |

Every recipe is arithmetically balanced. The defects are semantic: wrong account, wrong moment, wrong source of truth.

**R1 — Invoice finalized.** Assumes the provider will collect exactly `T − u`. Asaas does not guarantee that:
`value` can include interest/fine on late payment and discounts reduce it (asaas §3 `discount/interest/fine`,
`originalValue`). R2 then credits `customer_receivable` with `G ≠ T−u` and R3 debits `sales_clearing` with `G`:
**both accounts are left with a permanent residual** (F-07). No recipe for `finalized → void` (DOMAIN §2 allows it)
which must reverse R1 **and** the wallet part (R7 + R3(u)) (F-12). `T = u` gives a zero-amount posting, which
violates `amount > 0` (FM §2); state that zero legs are dropped (F-13). R1 says the wallet portion is "posted in the
same entry", while R7 says "followed by R3" and R3 says "same transaction as R2": pick one entry layout (minor).

**R2 — Payment confirmed.** Correct legs. Three problems: (a) the fee is booked at CONFIRMED from `value − netValue`,
but asaas §9.2.4 recommends booking it at RECEIVED and checking it against the extrato. `netValue` changes with
anticipation and installments (asaas §4 "Anticipation reduces net available"), so R4 moves a different `N` than
R2 left in `provider_receivable` and the account never zeroes. There is no fee-adjustment recipe (F-08). (b) "If
the fee is unknown, post it later": R3 with `proportional` **needs** `N` up front, so the deferral path cannot
produce R3 (F-08). (c) Synthesizing `payment.confirmed` from a PIX `PAYMENT_RECEIVED` (INTEGRATIONS §2) is
correct **only if** the synthetic path and a late real `PAYMENT_CONFIRMED` derive the same ledger key
`payment:{pp_id}:confirmed`. The docs never say so, so write it down and test it. Ordering (RECEIVED before
CONFIRMED) is otherwise handled.

**R3 — Split allocation.** (a) R3 runs unconditionally "same transaction as R2". For a `credit_purchase` (R6),
`sales_clearing` was never credited, so R3 drives it negative and books revenue/payee shares on a top-up. FM says
"no split on top-ups" but never says R3 is skipped. A mixed invoice (top-up line + service lines) needs R3 over
the service portion only (F-02). (b) Who takes part in the allocation is ambiguous. If only payees are allocated
("platform receives the rest"), largest remainder with a single payee is degenerate and **floors** (14850). The
worked example's 14851 only follows if the platform is a participant (F-11). (c) With a provider split, Asaas
computes `percentualValue` over `netValue` with its **own rounding (UNVERIFIED)**. Our share can differ from
Asaas's by 1 cent on every payment, and R5 then posts our `s_i` while Asaas moved its own amount: a reconciliation
break on every charge (F-10). (d) `fee_bearer = platform` with a provider split can only be expressed as
`fixedValue`, and needs Σs_i ≤ N, otherwise Asaas raises `PAYMENT_SPLIT_DIVERGENCE_BLOCK` (asaas §4) (F-10).

**R4 — Settlement.** Correct for the internal split. It recomputes `N` (see F-08). It is undefined for refunds or
chargebacks that happen **before** settlement: card D+30 sits in `provider_receivable`, yet R8/R9 credit
`provider_balance`, which leaves `provider_receivable` permanently debit and `provider_balance` understated (F-14).
`split.blocked` (divergence) means Asaas has frozen the funds, yet R4 has already made them "available" (F-14).

**R5 — Provider-executed split.** Correct legs, assuming the extrato shows the net credit and then a split debit
(UNVERIFIED, so confirm in task 4.2). **Ordering hole:** `PAYMENT_SPLIT_DONE` can arrive before `PAYMENT_RECEIVED`
(non-sequential sends, or redelivery). R5 then debits `payee_payable_available` (`no_overdraft`) before R4
credited it. The handler fails, retries and ends in the DLQ (F-05). The posting amount must be Asaas's split value
(`additionalInfo.splitId` → split `value`), not our recomputed `s_i` (F-10).

**R6 — Wallet top-up. BLOCKER.** `Dr customer_receivable / Cr customer_credits` happens at **invoice
finalization** ("invoice line type credit_purchase credits the wallet"). The customer can spend credits
(`customer_credits` available > 0) **before paying**, or after a card that is later charged back. R7's
`no_overdraft` gives no protection because the balance was never earned. On top of that, R8/R9 on a top-up debit
`platform_revenue`/payees, which never received anything, instead of `customer_credits` (F-02).

**R7 — Wallet consumption.** Balances and zeroes `sales_clearing`. **But** the R3 it triggers credits
`payee_payable_pending`, and only R4 (a provider settlement event) moves pending → available. Wallet consumption
never has a settlement, so **payee earnings from wallet consumption are stuck in pending forever** and can never
be paid out (F-06). Economics are also inconsistent: with `proportional`, a payee gets a share of the full `u`
when the customer pays from the wallet, but a share of `N` when the customer pays directly. Document this or
apply a fee basis to `u`.

**R8 — Refund. BLOCKER.**
1. **Provider split (R5 already done):** our payee liability was already extinguished by R5. Asaas reverts split
   transfers from the recipient subaccounts (`refundedSplits[{value,done}]`, asaas §3/§4), so our
   `provider_balance` only drops by `R − Σ refundedSplits.done`. R8 credits `provider_balance` with the full `R`
   **and** debits `payee_payable_*` again, which overstates the outflow and pushes the payee's liability negative.
   Because of `no_overdraft`, the residual is pushed into `chargeback_losses`. Result: a fake loss plus a ledger
   that does not match the extrato (F-01).
2. Only "a settled payment" is covered. Refunding a card payment before settlement must credit
   `provider_receivable` (F-14).
3. Asaas refunds are asynchronous (`refunds[].status PENDING|DONE|CANCELLED`, `PAYMENT_REFUND_IN_PROGRESS`,
   `PAYMENT_REFUND_DENIED`). R8 has no hold, so R10 can pay out the same money while the refund is in flight.
   Model the refund as two-phase, like R10 (F-15).
4. Partial refunds: per-refund largest-remainder allocations do not add up to the full reversal (each refund
   rounds independently). FM's "a full refund reverses R3 exactly" holds only for a single full refund. Nothing
   enforces "cumulative refunds ≤ original" (benchmark §5 line "tracked so cumulative reversals never exceed
   original") (F-16).
5. Idempotency key: `refunds[]` items carry **no id** (asaas §3 field list), so a key like `payment:{pp}:refunded`
   collides across partial refunds, and a webhook-event-id key double-posts when a `PAYMENT_UPDATED` refetch
   discovers the same refund (F-16).
6. "Shortfall → `chargeback_losses` + recoverable item" books an expense **and** a receivable for the same thing.
   Use `Dr payee_receivable:{p}` (asset) with a later write-off recipe (F-17).
7. Fee non-refundable + `proportional`: the platform alone absorbs `F` on refund, although the payee shared the fee
   on the way in. Write this down as an explicit policy (minor).

**R9 — Dispute.** Legs balance. (a) The disputed amount is `chargeback.value`, which is usually `G`, while only `N`
was ever credited. If the dispute happens before settlement, the hold must come from `provider_receivable`, not
`provider_balance`. (b) **Payee shares stay withdrawable during the dispute.** The payee can withdraw through R10,
and when the dispute is lost the platform eats the loss. On `dispute.opened`, move the disputed share
`payee_payable_available → payee_payable_held` (new account). (c) With a provider split, Asaas behaviour on the
recipients is UNVERIFIED, so assume F-01's structure. (d) Chargeback fees are not modeled. (e) A partially
refunded payment that is then disputed: dispute amount = remaining. Not stated (F-18).

**R10 — Payout.** The two-phase design is correct and the `no_overdraft` check is on the right account. (a) Asaas
`POST /transfers` lists no `externalReference` (asaas §5 field list), so ADR-0004's "look up by
`externalReference` before retry" **may not apply to transfers**. A timeout followed by a retry is a **double
payout** (F-03). (b) No `requested → failed` transition (submission rejected / validation refused); DOMAIN §2 only
has `submitted → failed`. (c) A PIX/TED return after `TRANSFER_DONE` cannot void a posted entry, so a reversal
recipe is needed. (d) Transfer fees (TED) are not booked, which causes a reconciliation break (F-19).
`TRANSFER_BLOCKED` is unmapped.

**Missing recipes (all major):** overpayment / second ProviderPayment paid for the same intent (DOMAIN allows N
attempts per intent; ADR-0004 keys by `pp_id`, so **both** post R2 and `customer_receivable` goes credit) (F-04);
payment received on a `canceled`/`failed` intent (DOMAIN makes both terminal, but Asaas `PAYMENT_RESTORED` and a
card retry after `CAPTURE_REFUSED` can still confirm) (F-04); `RECEIVED_IN_CASH` (no money at the provider; R4
must not run); reconciliation adjustment entries; opening balance.

### 1.2 Worked example (FM §5) — recomputed by hand
- G = 20000, F = 199 → N = 20000 − 199 = **19801**.
- Exact shares of N: doctor 0.75 × 19801 = **14850.75**; platform 0.25 × 19801 = **4950.25** (sum 19801).
- Floors: 14850 + 4950 = 19800 → leftover 1 cent → largest fraction (.75 > .25) → doctor. Doctor **14851**,
  platform share of N **4950**.
- `platform_revenue` = G − Σs = 20000 − 14851 = **5149**; platform net = 5149 − 199 = **4950** = 19801 − 14851. ✔
- Trial balance after settlement: Dr provider_balance 19801 + provider_fees 199 = 20000; Cr payee_payable_available
  14851 + platform_revenue 5149 = 20000; customer_receivable, sales_clearing and provider_receivable = 0. ✔
- **Verdict: arithmetic correct**, but only if the platform takes part in the allocation (F-11). The row text
  "0.75 × 19801 = 14850.75 → 14851" reads like independent rounding of one share; rewrite it to show the
  two-participant largest-remainder computation. The 14851 also has to match Asaas's own rounding of 75 % ×
  198.01 = 148.5075, which is UNVERIFIED (F-10).

## 2. Concurrency and integrity (ADR-0003 / 0004 / 0005)

| # | Hole | Where | Consequence |
|---|---|---|---|
| C1 | Lock order is "ascending id **per entry**"; one UoW posts several entries (R2 + R3 + R4 in the PIX path; R1 + R7 + R3). Locks taken entry by entry are not globally ordered. | ADR-0003 §4 | Deadlocks between concurrent webhook handlers. Lock the **union** of accounts for the whole UoW once, sorted. |
| C2 | No lock hierarchy between aggregate rows (intent, invoice, payout) and account rows. | ADR-0003, ARCH §4.2 | Deadlock between a webhook (intent → accounts) and a payout (accounts → payout). Rule: aggregates first (fixed type order), then accounts. |
| C3 | Lazy account provisioning "on first use" races. | FM §3 | Unique violation / lost update. Use `INSERT … ON CONFLICT DO NOTHING` and then `SELECT … FOR UPDATE`. |
| C4 | The deferred balance trigger fires on **posting** insert only. | ADR-0003 §2 | An entry with 0 or 1 postings, a posting whose currency ≠ the account currency, or a posting whose account belongs to another project all pass. Add an entry-level constraint trigger (≥2 postings, balanced per currency), a posting-currency = account-currency check, and a composite FK `(project_id, account_id)`. |
| C5 | Balances are updated by application code; triggers only guard immutability. | ADR-0003 §4 | Any SQL path that inserts postings drifts balances (detected only by the nightly job). Update balances in the posting trigger or restrict inserts to one SQL function. Use a DB role without `UPDATE/DELETE` and without trigger-disable rights (owner can `DISABLE TRIGGER`). |
| C6 | Key `payment:{pp_id}:confirmed` is per *attempt*, not per *intent*. | ADR-0004 | Two attempts paid → two R2 (F-04). Add a per-intent "captured" guard: status CAS plus overpayment routing. |
| C7 | Payload-hash mismatch on a ledger key → "conflict". | ADR-0003 §6 | A legitimately changed `netValue` on refetch makes the handler retry the conflict forever → DLQ. A conflict must park the event and raise a reconciliation break, never retry. |
| C8 | **Lease expiry → double execution of side effects.** The inbox (`UNIQUE(handler,event_id)`) protects DB effects only. The `invoice.finalized` handler calls Asaas *outside* the tx (ARCH §4.1 step 4 + §4.2). Two workers past the lease both `POST /payments`. "Look up by externalReference" is check-then-act and Asaas search consistency is unknown. | ADR-0005, ADR-0004 | **Duplicate charges / duplicate transfers** (F-03). Commit a state CAS (`UPDATE intent SET status='submitting', attempt_token=? WHERE status='requires_payment'`) before the call. Add fencing: a delivery `lease_token` checked on every completion write. Heartbeat-renew the lease for calls longer than the lease. |
| C9 | Completion writes are not fenced. | ADR-0005 | Worker A (expired) marks `succeeded` or `retry_scheduled` over worker B's live attempt. Compare-and-set on `lease_token`. |
| C10 | **NOTIFY/cursor loss.** UUIDv7 ids are generated before commit, so commit order ≠ id order. SSE `Last-Event-ID` and any "events after id X" cursor (Explorer, catch-up) **skip** late-committing events permanently. | ADR-0005, ADR-0010 | SSE silently misses payments. Serve only events below `pg_snapshot_xmin(pg_current_snapshot())` (store `xid8` per event), or re-read a safety window. A NOTIFY lost while LISTEN reconnects is covered only if the reconnect re-reads from the cursor; say so. |
| C11 | `pg_notify` inside business txs: a stalled LISTEN connection fills the notify queue, and once it is full **commits that NOTIFY fail**. NOTIFY also takes a global commit-time lock. | ADR-0005/0010 | A stuck SSE replica can block payment commits. Do NOTIFY from the dispatcher or after commit (polling is already the fallback), monitor `pg_notification_queue_usage()`. |
| C12 | Fan-out of `event_deliveries` is unspecified. | ADR-0005 | Created in the business tx: a subscription added concurrently misses events. Created later by a scanner: inherits C10. Specify one approach. |
| C13 | No per-subject ordering in the dispatcher; it is unclear whether recipes run in the normalization tx or in `payment.*` handlers (ARCH §4.1 step 5). | ARCH §4.1 | R4 before R2/R3, R5 before R4 (F-05). Post ledger recipes **in the same tx as the payment state transition**, serialized by `SELECT … FOR UPDATE` on the provider_payment row. Out-of-order webhooks then just become state-machine input. |
| C14 | Session-level `pg_try_advisory_lock` breaks behind transaction-pooling (PgBouncer). Harmless here because emission is idempotent by `(schedule, due_at)`. | ADR-0005 | OK as long as pooling is session-mode; note it. |
| C15 | HTTP idempotency: a record left `in-flight` by a crashed request answers 409 forever; key scope `(project,key)` ignores the endpoint. | ADR-0004 | Add an in-flight lease timeout; scope by `(project, method, path, key)`. |
| C16 | Receipts are unique on `(provider, provider_event_id)`. | ADR-0004, DOMAIN inv. 4 | With one subaccount per tenant (asaas §9.2.8), event-id uniqueness across accounts is UNVERIFIED. Use `(provider_account_id, provider_event_id)`. |

## 3. Architecture

**Transaction boundaries.** ARCH §4.2 (persist → commit → call → record) is right but incomplete:
(1) a crash between call and record leaves an intent in `submitting` with an unknown outcome, so it needs a
recovery sweeper (`find_by_external_reference` with backoff); nobody owns that. (2) The webhook can arrive
**before** "record result" commits (Asaas fires `PAYMENT_CREATED` immediately). The webhook path must resolve by
`externalReference = intent id`, upsert the provider_payment under `UNIQUE(provider_account, provider_payment_id)`,
and the record step must merge. (3) The same gap applies to refunds and transfers (no Asaas idempotency).

**State machine (DOMAIN §2) conflates orthogonal dimensions.** Capture, settlement, refunded amount and dispute are
independent (a payment can be `settled` **and** `partially_refunded` **and** `disputed`). A single enum makes the
promised "status precedence table" (never written down anywhere) impossible to define. Use separate fields
(`capture_status`, `settled_at`, `refunded_amount`, `dispute_status`) and derive the display status. Also:
`canceled` and `failed` must accept late success (F-04), and `PAYMENT_RESTORED` has no transition.

**Module boundaries.** `wallets` owning "posting recipes (FM §4)" (ARCH §3) is a smell: R2–R5 and R8–R10 are
payments recipes, so payments would depend on wallets for its core behaviour. Put recipes in a `ledger.posting_rules`
application facade (or one `accounting` module) that both billing and payments call. PLAN §3 lists
`catalog/pricing` and `settlements/payouts` contexts that ARCH §3 does not have; pick one list.

**Overengineered for a small-team portfolio.** 17 contexts + import-linter + manifest DSL + AI analyst + MCP +
SSE + Standard-Webhooks secret rotation + 7 pricing models + subscriptions + reconciliation, all labelled
*Implemented*, on a bleeding-edge toolchain (Py 3.14, SQLAlchemy 2.1, TS 7, Vite 8). Recommend collapsing to ~8
modules (platform/events/webhooks/realtime; identity+projects+audit; customers; ledger+wallets; billing+pricing+
metering; payments+payouts; reconciliation; integrations+intelligence). Demote subscriptions, 3 of the 7 pricing
models and webhook secret rotation to *Planned* until the payment → ledger → reconciliation slice works end to
end. AES-GCM data-key rotation with re-encryption is also more than this stage needs.

**Missing — what a hiring reviewer expects to find:**
- A **reconciliation design** (matching keys, break taxonomy, *adjustment posting recipes*). It is the PLAN's
  headline step but has no ADR and no recipe.
- `effective_at` semantics: backdating policy, accounting periods / close, balance-as-of queries.
- Webhook ingestion ADR: status precedence table, refetch policy, parking/unknown events, 14-day Asaas retention
  catch-up (asaas §6).
- **LGPD**: CPF/e-mail are personal data. Right to erasure vs an immutable ledger → keep PII out of
  postings/metadata (reference `customer_id` only) and document crypto-shredding or pseudonymization.
- Failure-mode table (Asaas down, DB failover, DLQ growth), backups/PITR, SLOs and alerts, load numbers for the
  hot-account serialization accepted in ADR-0003.
- Naming drift: INTEGRATIONS `payment.canceled`/`split.done`/`payment.refunded` vs research §9.2.5
  `payment.cancelled`/`split.settled`/`refund.*`. INTEGRATIONS also leaves unmapped `PAYMENT_REFUND_IN_PROGRESS`,
  `_REFUND_DENIED`, `_SPLIT_CANCELLED`, `_DIVERGENCE_BLOCK_FINISHED`, `_ANTICIPATED`, `_RECEIVED_IN_CASH_UNDONE`,
  `TRANSFER_BLOCKED`. DOMAIN says corrections go "via credit notes" while ADR-0007 says credit notes are *Planned*.

## 4. Security gaps (SECURITY.md)

1. **Webhook payloads are trusted for money.** Asaas authenticates with a static shared token only (no body
   signature, no timestamp). A leaked token or a replay of a captured body can inject events. Rule: **money-moving
   recipes post only from a `get_payment`/`get_transfer` refetch**, never from payload amounts. Also add token
   rotation and the optional IP allowlist (asaas §1).
2. **Cross-tenant event confusion.** Bind receipt → `provider_account` (URL) → project, and verify that the
   intent resolved through `externalReference` belongs to the same project/provider account before acting.
   Without that, a valid token on account A can drive intents of project B.
3. **No payout authorization control.** Enable Asaas's withdrawal-validation webhook (asaas §5) so that a leaked
   Asaas API key cannot drain the account. The Hub approves a transfer only when it matches a pending R10 entry.
4. **No maker-checker on money movement.** Refunds, payouts, manual ledger adjustments and manifest changes that
   touch `splits[]`/payees need mandatory four-eyes (ADR-0008 makes it *optional*) plus step-up auth.
5. **No operator MFA** (TOTP/WebAuthn) for a console that can move money. Lockout policy is unspecified beyond
   "throttling".
6. **AI/MCP:** read-only MCP tools expose customer PII to external LLM clients. Product-supplied descriptions or
   OpenAPI documents are a prompt-injection vector into proposed `splits[]` (for example, redirecting a share to
   an attacker payee). Needed: PII minimization in MCP reads, a highlighted money-diff in approval, and mandatory
   four-eyes for money-affecting fields.
7. **DB privilege separation** missing: runtime role ≠ migration/owner role; `REVOKE UPDATE, DELETE` on
   postings/entries/audit. Triggers alone do not stop a role that can disable them (C5).
8. **PII in logs:** redaction lists only secrets; add CPF/CNPJ, e-mail and phone. PII at rest is not encrypted.
9. Minor: API-key pepper rotation; AES-GCM associated data should include table + column + project, not just the
   row id; CSP/security headers for the SPA; container image scanning/SBOM; webhook receipt replay window.
